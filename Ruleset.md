App development Documentary Ruleset:
All team members must follow these general rules throughout the entire project:
1. Develop a reliable, user-friendly, secure, accessible, and maintainable application that meets the approved project requirements and supports all required platforms.
2. Use only the approved technologies, tools, frameworks, database systems, and project architecture. Any proposed change must be discussed and approved by the team leader before implementation.
3. Store all source code, documentation, configurations, testing records, and project files in the official repository. Keep the repository organized and remove unnecessary or duplicate files.
4. Always work from the latest version of the project. Keep the main branch stable, tested, and deployable. Use separate branches for features, bug fixes, documentation, and testing, and follow the agreed branch naming and commit message conventions.
5. Do not push unfinished, untested, broken, or unauthorized changes directly to the main branch. Review, test, and obtain the required approval before merging changes.
6. Use clear and meaningful commit messages. Inform the responsible team member before modifying their work.
7. Never commit passwords, API keys, database credentials, tokens, confidential configuration values, or other sensitive information to the repository or public platforms.
8. Write clean, readable, maintainable, organized, and consistently formatted code. Use meaningful names, avoid unnecessary duplication, reuse code where appropriate, and add comments only when they provide useful clarification.
9. Keep frontend, backend, database, API, and other system responsibilities properly separated. Follow the approved architecture and project conventions.
10. Validate and sanitize all user inputs, requests, forms, and stored data before processing them. Prevent invalid, incomplete, duplicate, inconsistent, unauthorized, or unsafe operations.
11. Handle errors properly and provide clear, consistent, understandable, and useful messages to users and developers.
12. Do not remove, change, or replace existing functionality without team discussion and approval.
13. Use the approved database technology and design tables, relationships, data structures, keys, constraints, and data types according to the approved requirements. Maintain data consistency and integrity, use parameterized queries or prepared statements, protect database credentials, and back up important data when required.
14. Follow the approved backend framework and API architecture. Implement required authentication, authorization, session functionality, endpoints, and services. Use appropriate HTTP methods, status codes, response formats, and error messages. Protect restricted endpoints and sensitive operations from unauthorized access.
15. Test every completed endpoint using the approved testing tools and ensure reliable communication between the API, database, and frontend. Record bugs, issues, and API problems in the project issue tracker.
16. Follow the approved frontend requirements, design guidelines, and system rules. Maintain consistency in colors, fonts, buttons, spacing, navigation, layouts, loading indicators, validation messages, warnings, and error messages.
17. Provide all required screens and user functions. Prevent users from submitting empty, invalid, or incomplete forms. Ensure displayed information matches the actual system data.
18. Keep the interface simple, responsive, accessible, and easy to understand. Test it on all required platforms, devices, and screen sizes.
19. Require authentication before users access protected functions. Ensure that create, view, update, and delete operations work correctly where applicable.
20. Keep related records, system values, transactions, calculations, summaries, reports, notifications, alerts, and displayed totals synchronized and accurate after every operation.
21. Apply configured thresholds, limits, business rules, and project requirements consistently. Do not implement features outside the approved scope without team approval, and clearly identify excluded features.
22. Test every feature after development and whenever it is modified. Test valid and invalid inputs, authentication, authorization, required fields, create, view, update, delete operations, normal cases, edge cases, error conditions, calculations, transactions, records, prohibited operations, and platform compatibility.
23. Perform regression testing after major changes. Document bugs with clear descriptions and reproduction steps, fix critical and high-priority bugs before demonstrations or release, and record testing results and unresolved issues.
24. Assign clear responsibilities to every team member. Complete assigned tasks on time and according to project standards. Communicate progress, delays, risks, technical problems, and incomplete tasks promptly.
25. Assist one another when necessary. The team leader is responsible for coordination, repository management, approvals, and final reviews. Developers are responsible for implementing, testing, and documenting their work. Project managers or coordinators are responsible for schedules, requirements, documentation, and scope. Quality assurance members are responsible for testing, reporting bugs, verifying fixes, and checking compatibility.
26. Every feature, improvement, or bug fix must be reviewed, planned, implemented, tested locally, committed, pushed, reviewed, corrected when necessary, approved, and merged only after meeting the project requirements.
27. Keep project documentation updated, including installation instructions, dependencies, usage information, database setup, environment configuration, user documentation, schedules, task lists, feature checklists, progress records, completed features, known issues, testing results, important decisions, demonstration materials, presentation notes, and anticipated questions.
28. Follow the approved project proposal and requirements. Discuss and approve major changes before implementation. Evaluate changes based on their effect on time, workload, cost, security, scope, and system stability.
29. Prioritize required and core functionality. Complete and test required features before adding optional improvements. Record approved changes and reject changes that are unnecessary, unsafe, or outside the approved scope.
30. Protect user, system, and project information. Use secure authentication, authorization, coding, input validation, data storage, API, and database practices. Report security issues immediately to the team leader.
31. Before completion, verify that all required features work correctly, authentication and authorization function properly, data operations are accurate, invalid inputs and prohibited operations are prevented, transactions and calculations update correctly, reports and displayed totals match stored data, the application works on all required platforms, critical bugs are resolved, security and privacy requirements are reviewed, documentation is complete, testing results and known issues are recorded, practice demonstrations or release reviews are completed, and every member understands their responsibilities and the system architecture.
32. All team members must follow these general rules, communicate respectfully, maintain quality and security, document their work, cooperate with one another, and contribute to delivering a functional, reliable, secure, and maintainable application.
